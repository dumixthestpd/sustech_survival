## Unified Authorizer Interface

All services (BB, TIS, Lib, RSC, WoS, CNKI, etc.) should share one interface:

```python
auth = get_auth("bb")        # → BBAuth instance
auth = get_auth("rsc")       # → RSCAuth instance
ok   = auth.login()          # → bool, sets auth.browser / auth.page
cookies = auth.cookies()     # → dict for requests/Playwright
auth.close()                  # → cleanup
```

Every authorizer exposes the same contract. The caller never knows or cares which backend (CAS, CARSI, Shibboleth, OAuth, etc.) is underneath.

Open questions:
- Should `cookies` be Playwright-format (list of dicts) or requests-format (dict of name→value)?
- Should `close()` be implicit via context manager (`with get_auth("bb") as auth:`)?
- Should each auth have a `health_check()` method separate from `login()`?

## Persistent Browser Context

Currently every operation launches a fresh Chromium, authenticates, does one thing, closes. This is slow (5–10s per operation) and causes more load on CAS/CARSI IdPs.

Better: maintain a long-lived Playwright context per service, serialized to disk between sessions:

```python
ctx = ContextStore.load("bb")  # → Playwright browser context
if ctx.expired():
    ctx = await refresh(ctx)   # → get new cookies via CAS
ctx.attach_to(page)            # → reuse existing context
```

Challenges:
- Browser context serialization is not trivial (cookies + localStorage + sessionStorage)
- Need to handle browser crashes / stale contexts
- Hard to debug when something goes wrong

## TIS Auto-Submission

TIS (teaching evaluation) has a known flow:
1. GET form → extract course list from `<select>`
2. POST each course with evaluation scores
3. Confirm submission

This is fully deterministic and doesn't need a browser. Could be a headless `requests` flow like CAS.

Current blockers:
- TIS uses a different CAS endpoint than BB/Lib (`https://tis.sustech.edu.cn/cas`)
- `TISAuth` creds_file override was removed (uses root `credentials.txt` now) — verify this works

## CNKI Direct PDF Download

CNKI currently requires browser interaction. The CNKI page loads a JavaScript-based PDF viewer. The actual PDF URL pattern is known: `https://kns.cnki.net/kns8s/files/{hash}.pdf`.

If we can extract the file hash from the page (via Playwright), subsequent downloads could use `requests.get()` directly — no browser needed.

Risks:
- CNKI hashes are time-varying and account-bound
- May violate CNKI terms of service

1. Check all courses each morning

## BB Assignment Discovery

Currently `submit.py` requires `course_id` and `content_id` to be known in advance. A discovery layer could:

```python
courses = discover_courses()        # → [(name, course_id)]
assignments = discover_assignments(course_id)  # → [(title, content_id, due_date)]
```

Already partially exists in `courses.py` and `download.py`. Needs cleanup + unification into a simple API.

## Unified Paper Research Tool

Currently: arXiv (direct PDF), Crossref (metadata), Semantic Scholar (OA PDFs), Europe PMC (OA). Each is a separate function call.

Future: one `paper.search("electrochromic", scope="free")` that:
1. Searches Crossref for DOI + metadata
2. Checks each DOI against multiple free-full-text sources in parallel
3. Returns ranked results with direct PDF URLs

Could also integrate with Lib (institutional access) to check if non-OA papers are available via SUSTech's subscriptions.

## Unified Submission API

```python
submit(
    service="bb",
    course="MSE212",        # or course_id
    assignment="Exp Report 1",  # fuzzy match
    files=["report.pdf"],
    check_dedup=True,
)
```

- Resolve `MSE212` → `course_id`
- Resolve "Exp Report 1" → `content_id` (fuzzy match against assignment names)
- Check dedup (same filename? same MD5?)
- Submit
- Return confirmation

This would be the highest-level user-facing API. Everything else is implementation detail.
